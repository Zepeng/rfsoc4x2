# External PPS Trigger for Four-Channel RFSoC4x2 ADC Capture
This guide extends the four-channel RFSoC4x2 Vitis ADC platform so that ADC_D, ADC_C, ADC_B, and ADC_A are all captured as readout channels. The acquisition trigger comes from the board's dedicated pulse-per-second (`1PPS`) SMA input instead of an ADC threshold crossing.

The base four-channel platform is described in:

- [Vitis 2023.1 Classic IDE guide](vitis_adc_platform_classicIDE.md)
- [Vitis 2023.2.1 Unified IDE guide](vitis_adc_platform.md)

## Implementation Order
Make this change in measured stages. The PPS adapter adds an external trigger, but it does not resolve cross-tile ADC clock alignment by itself.

1. Build and test the current four-channel ADC-threshold design before adding PPS logic. Follow the **Validate the Four-Channel Hardware Build** section in the [Classic IDE guide](vitis_adc_platform_classicIDE.md#validate-the-four-channel-hardware-build) or [Unified IDE guide](vitis_adc_platform.md#validate-the-four-channel-hardware-build). Split one sine wave into all four ADC inputs, capture several frames, and repeat after reprogramming or power cycling the board.
2. Check every channel for continuous samples and compare the phase relationship between the tile-0 channels (`ADC_D`, `ADC_C`) and tile-2 channels (`ADC_B`, `ADC_A`).
3. Decide whether tile synchronization is required. The current platform intentionally drives both RFDC AXI4-Stream interfaces from `clk_adc0`, while RFDC multi-tile synchronization remains disabled. If the measured waveforms are continuous and the observed cross-tile timing behavior is sufficient for the application, defer multi-tile synchronization and record that limitation. If tile-2 data is corrupted, the cross-tile phase changes after restart, or deterministic tile-to-tile timing is required, implement and validate RFDC multi-tile synchronization or an explicit clock-domain-crossing architecture before relying on four-channel timing measurements.
4. Confirm the PPS front-end behavior on the board before editing the platform: pin mapping, I/O voltage, accepted input amplitude, pulse-width behavior, and which conditioned output is appropriate.
5. Add the static PPS adapter, regenerate the platform, update HLS and the host, then rebuild and deploy the complete SD-card image.
6. Decide whether best-effort single-shot capture is sufficient. If every external pulse must produce a retained frame, implement ping-pong buffers or a continuous event queue before production use.

## 1. Hardware Architecture
The RFSoC4x2 board conditions the `1PPS` SMA input and exposes two signals to the programmable logic:

| Signal | FPGA pin | Use |
|---|---|---|
| `IRIG_TRIG_OUT` | `AH13` | Output of the Schmitt-trigger branch. Use this as the initial acquisition trigger. |
| `IRIG_COMP_OUT` | `AJ13` | Output of the LMV7235 comparator branch. Leave unused initially; expose it only as an optional diagnostic. |

Figure 6 of the [RFSoC4x2 Reference Manual](https://www.realdigital.org/downloads/4b98c421901794107cd1e25e208fe002.pdf) shows separate Schmitt-trigger, ADS7885S ADC, and LMV7235 comparator branches after the PPS input network. The LMV7235 therefore does not set the timing of the recommended `IRIG_TRIG_OUT` path. Appendix A states that signals use `LVCMOS18` unless otherwise noted. Before programming the design, confirm `AH13` and its bank voltage against the official master constraints or the synthesized I/O report.

### Onboard Schmitt-Trigger Branch
The Schmitt trigger is generated by fixed hardware on the RFSoC4x2 board. It is not implemented in Vivado or HLS, and it does not require FPGA register programming. The [RFSoC4x2 schematic](https://www.realdigital.org/downloads/1859152f898cfb0d53c4792e23e91b35.pdf) identifies the buffer as `IC22`, a TI `SN74AUP1G17DCKR`.

The relevant signal path is:

```text
1PPS SMA connector
  -> onboard termination, protection, and AC-coupling network
  -> SN74AUP1G17DCKR Schmitt-trigger buffer at approximately 3.3 V
  -> IRIG_TRIG_OUT_3V3
  -> NVT2008BQ level translator
  -> IRIG_TRIG_OUT in the 1.8 V FPGA I/O domain
  -> FPGA pin AH13
```

The Schmitt-trigger buffer applies hysteresis:

```text
input rises above VT+  -> output becomes high
input falls below VT-  -> output becomes low
VT+ - VT-              -> hysteresis
```

This prevents noise or ringing near the switching point from producing repeated trigger edges. The [TI SN74AUP1G17 datasheet](https://www.ti.com/lit/ds/symlink/sn74aup1g17.pdf) specifies the following ranges at `VCC = 3.0 V`; use them as representative values because the board supplies the buffer at approximately `3.3 V`:

| Parameter | Range |
|---|---:|
| Positive-going threshold `VT+` | `1.88 V` to `2.29 V` |
| Negative-going threshold `VT-` | `0.88 V` to `1.24 V` |
| Hysteresis `VT+ - VT-` | `0.79 V` to `1.31 V` |
| Propagation delay at `3.3 V` | Up to `5.1 ns` |

These voltages apply at the Schmitt-buffer input after the board's analog conditioning network. They are not the required voltages at the external SMA connector.

Use this PL datapath:

```text
1PPS SMA
  -> onboard PPS signal conditioning
  -> IRIG_TRIG_OUT / AH13
  -> pps_trigger_axis static RTL
  -> PPS_TRIG_AXIS
  -> dummy_kernel_1.ext_trigger_in

ADC_D / ADC_C / ADC_B / ADC_A
  -> RFDC AXI4-Stream outputs
  -> dummy_kernel_1 ADC readout inputs
```

The static RTL adapter synchronizes the asynchronous trigger into the common RFDC stream clock domain and presents its current level as one continuously valid AXI4-Stream word per cycle. The HLS kernel consumes that stream in lockstep with the four RFDC streams.

The updated four-channel platform keeps:

| Setting | Value |
|---|---:|
| RFDC converter sample rate | `4.9152 GS/s` |
| ADC decimation | `8` |
| Per-channel ADC output rate | `614.4 MS/s` |
| Samples per RFDC AXI4-Stream word | `8` |
| Common RFDC AXI4-Stream clock | `clk_adc0`, `76.8 MHz` |
| Vitis linker clock | `id=3:dummy_kernel_1` |

### Trigger Latency and Accuracy
The captured ADC sample index is not the exact time at which the external analog edge arrived at the SMA connector. For the recommended `IRIG_TRIG_OUT` path, the timing budget includes:

- the external source edge and cable delay;
- the board's Schmitt-trigger threshold and propagation delay;
- the two-flip-flop synchronizer and registered AXI4-Stream adapter in the `76.8 MHz` `clk_adc0` domain;
- the kernel's rising-edge decision on one eight-sample RFDC AXI4-Stream word.

The on-chip contribution is quantized in `13.02 ns` AXI4-Stream clock periods and eight-sample words. Fixed latency can be calibrated with a scope, but the board reference manual does not specify the Schmitt-trigger propagation-delay distribution.

If `IRIG_COMP_OUT` is evaluated later, its timing budget is different. The [TI LMV7235 datasheet](https://www.ti.com/lit/ds/symlink/lmv7235.pdf) gives typical comparator propagation delays of approximately `89 ns`, `82 ns`, and `75 ns` for `20 mV`, `50 mV`, and `100 mV` input overdrive at `5 V` with a `15 pF` load. That branch can add amplitude- and slew-dependent time walk. A useful first-order estimate is:

```text
timing uncertainty ~= voltage uncertainty / input slew rate
```

Use a scope measurement at the board input when sub-clock trigger accuracy matters. An ILA is useful for digital sequencing after the conditioned FPGA input, but it cannot characterize the analog front end precisely.

## 2. Trigger Signal for Initial Testing
The `1PPS` connector name describes the intended timing application. It is not a strict `1 Hz` repetition-rate limit.

Apply the external source only to the board's `1PPS` SMA connector. Do not attempt to drive the onboard buffer or FPGA pin directly. Start with a conservative function-generator signal:

| Setting | Initial value |
|---|---:|
| Waveform | Pulse or square wave |
| Frequency | `1 Hz`, then increase to `60 Hz` |
| Pulse width | `1 us` to `1 ms` |
| Amplitude | Start at `1 Vpp` |
| Offset | `0 V` |
| Generator load setting | `50 ohm` |

Figure 6 of the reference manual depicts an AC-coupling network at the PPS SMA input. Use a pulse train with a distinct low interval rather than a constant high level. Verify the waveform at the cable endpoint with an oscilloscope before connecting it to the board. Also verify the conditioned response for the intended source pulse width, especially before using a GPS PPS source with a wide high interval. Increase amplitude gradually only if the PL input does not toggle. The board reference manual does not state a maximum supported external PPS amplitude, so do not assume that a `5 V TTL` pulse is safe.

The Schmitt-buffer threshold table above cannot be used as a direct SMA amplitude requirement because the onboard input network changes the waveform before it reaches the buffer. During bring-up:

1. Verify the generator waveform at the cable endpoint with an oscilloscope.
2. Connect the cable to the `1PPS` SMA input.
3. Confirm that `IRIG_TRIG_OUT` toggles using an ILA or oscilloscope.
4. Increase the source amplitude gradually only if the conditioned signal does not toggle.
5. Repeat the measurement with the intended production pulse width and repetition rate.

At `60 Hz`, trigger edges are separated by approximately `16.7 ms`. After a trigger, the current kernel needs about `21.3 us` for the post-trigger interval and `26.7 us` to copy the ring buffer to DDR, before variable host-side XRT relaunch latency is included. The present design does not queue trigger events: an edge that arrives during copy or relaunch can be missed. A single-shot or best-effort `60 Hz` test is reasonable. If every pulse must produce a retained frame, treat ping-pong buffers or a continuous event queue as a requirement rather than an optional optimization.

## 3. Add the Static RTL Trigger Adapter
Create a new Verilog source file named `pps_trigger_axis.v` in the Vivado hardware project:

```verilog
module pps_trigger_axis (
    input  wire        aclk,
    input  wire        aresetn,
    input  wire        pps_in,
    output wire [31:0] m_axis_tdata,
    output wire        m_axis_tvalid,
    input  wire        m_axis_tready
);

(* ASYNC_REG = "TRUE" *) reg [1:0] pps_sync;
reg [31:0] axis_data;
reg axis_started;

always @(posedge aclk) begin
    if (!aresetn) begin
        pps_sync <= 2'b00;
        axis_data <= 32'b0;
        axis_started <= 1'b0;
    end else begin
        pps_sync <= {pps_sync[0], pps_in};
        axis_started <= 1'b1;
        if (m_axis_tready)
            axis_data <= {31'b0, pps_sync[1]};
    end
end

assign m_axis_tdata = axis_data;
assign m_axis_tvalid = axis_started;

endmodule
```

The adapter keeps `m_axis_tdata` stable when `m_axis_tready` is low, as required by AXI4-Stream. The two-flip-flop synchronizer prevents the asynchronous external input from feeding the HLS kernel directly. The registered `axis_started` flag makes the free-running stream valid after reset without tying `TVALID` combinationally to the reset net.

If Vivado does not infer the `m_axis` interface when the module is added to the block design, add these attributes immediately before the corresponding ports in the module declaration:

```verilog
(* X_INTERFACE_INFO = "xilinx.com:signal:clock:1.0 aclk CLK" *)
(* X_INTERFACE_PARAMETER = "XIL_INTERFACENAME aclk, ASSOCIATED_BUSIF m_axis, ASSOCIATED_RESET aresetn" *)
input  wire        aclk,
(* X_INTERFACE_INFO = "xilinx.com:signal:reset:1.0 aresetn RST" *)
(* X_INTERFACE_PARAMETER = "XIL_INTERFACENAME aresetn, POLARITY ACTIVE_LOW" *)
input  wire        aresetn,
(* X_INTERFACE_INFO = "xilinx.com:interface:axis:1.0 m_axis TDATA" *)
output wire [31:0] m_axis_tdata,
(* X_INTERFACE_INFO = "xilinx.com:interface:axis:1.0 m_axis TVALID" *)
output wire        m_axis_tvalid,
(* X_INTERFACE_INFO = "xilinx.com:interface:axis:1.0 m_axis TREADY" *)
input  wire        m_axis_tready
```

## 4. Add the PPS Pin Constraint
Create `pps_trigger.xdc` in the Vivado hardware project:

```tcl
set_property PACKAGE_PIN AH13 [get_ports IRIG_TRIG_OUT]
set_property IOSTANDARD LVCMOS18 [get_ports IRIG_TRIG_OUT]
```

The top-level block-design port name must match `IRIG_TRIG_OUT`.

Before generating the bitstream, inspect the synthesized I/O report and confirm that `IRIG_TRIG_OUT` resolves to `AH13` with `LVCMOS18`.

## 5. Update the Vivado Block Design
In the static Vivado platform block design:

1. Add an external input port named `IRIG_TRIG_OUT`.
2. Add `pps_trigger_axis` as a module reference named `pps_trigger_axis_0`.
3. Connect the trigger input:

   ```text
   IRIG_TRIG_OUT -> pps_trigger_axis_0/pps_in
   ```

4. Connect the adapter to the same common RFDC AXI4-Stream clock used by the four ADC streams:

   ```text
   usp_rf_data_converter_0/clk_adc0
     -> pps_trigger_axis_0/aclk
   ```

5. Connect the matching active-low reset:

   ```text
   proc_sys_reset_clk_adc0/peripheral_aresetn
     -> pps_trigger_axis_0/aresetn
   ```

6. Export the adapter AXI4-Stream interface to Vitis:

   ```tcl
   set_property PFM.AXIS_PORT {
     m_axis {
       type "M_AXIS"
       sptag "PPS_TRIG_AXIS"
       is_range "false"
     }
   } [get_bd_cells /pps_trigger_axis_0]
   ```

7. Validate the block design:

   ```tcl
   validate_bd_design
   save_bd_design
   ```

8. Generate the bitstream and export a new `.xsa` with the bitstream included.

The PPS adapter changes the static Vivado hardware platform. Regenerate the Vitis platform from the updated `.xsa` before rebuilding the Vitis application.

## 7. Update the HLS Kernel
Keep the four ADC readout streams. Add a fifth AXI4-Stream input for the synchronized external trigger.

The existing kernel uses the legacy name `trigger_in` for ADC_C because that channel previously provided the threshold trigger. It can remain named `trigger_in` to minimize code churn, but it is now captured only as ADC_C readout data.

Add this type:

```cpp
typedef ap_uint<32> trigger_pkt;
```

Update the kernel signature:

```cpp
void dummy_kernel(ap_uint<PACKED_WIDTH>* buffer0,
                  hls::stream<pkt>& data_in,
                  hls::stream<pkt>& trigger_in,
                  hls::stream<pkt>& adc_b_in,
                  hls::stream<pkt>& adc_a_in,
                  hls::stream<trigger_pkt>& ext_trigger_in,
                  unsigned int size,
                  unsigned int output_words) {
#pragma HLS INTERFACE m_axi port = buffer0 bundle = gmem0
#pragma HLS INTERFACE axis port = data_in
#pragma HLS INTERFACE axis port = trigger_in
#pragma HLS INTERFACE axis port = adc_b_in
#pragma HLS INTERFACE axis port = adc_a_in
#pragma HLS INTERFACE axis port = ext_trigger_in
```

Remove the `trigger_threshold` kernel argument and the ADC_C threshold-comparison state. Add external-trigger state before the acquisition loop:

```cpp
bool previous_ext_trigger_level = false;
```

Inside the existing pipelined `capture_adc_c_threshold` loop, read the external trigger once per ADC word and detect its rising edge:

```cpp
ap_uint<PACKED_WIDTH> packed =
    read_packed_word(data_in, trigger_in, adc_b_in, adc_a_in);
trigger_pkt ext_trigger_word = ext_trigger_in.read();

bool ext_trigger_level = ext_trigger_word[0];
bool crossing = !previous_ext_trigger_level && ext_trigger_level;
previous_ext_trigger_level = ext_trigger_level;
```

The loop must retain:

```cpp
#pragma HLS PIPELINE II = 1
```

After rebuilding HLS, confirm that the acquisition loop still achieves `II=1`.

## 11. Verify the Trigger on the Board
An Integrated Logic Analyzer (`ILA`) is optional. It is useful during initial PPS bring-up but is not required in the production design. The recommended approach is to add one narrow native-probe ILA core inside the static Vivado platform next to `pps_trigger_axis_0`.

Clock the ILA from the same free-running RFDC stream clock used by the PPS adapter and HLS kernel:

```text
usp_rf_data_converter_0/clk_adc0
```

The ILA probes must be synchronous to the ILA clock. AMD also requires the debug clock to remain stable and free-running during debug-core discovery and measurement. Configure the RF reference clocks before attempting to use Hardware Manager. Otherwise, Vivado may report that the debug cores cannot be detected.

Expose narrow debug outputs from `pps_trigger_axis` as needed and probe:

```text
pps_trigger_axis_0/pps_sync[1]
pps_trigger_axis_0/m_axis_tdata[0]
pps_trigger_axis_0/m_axis_tvalid
pps_trigger_axis_0/m_axis_tready
pps_trigger_axis_0/aresetn
```

Optionally probe the raw `IRIG_TRIG_OUT` port as a coarse diagnostic. It is asynchronous to `clk_adc0`, so do not use the sampled raw edge to measure exact trigger latency. Do not probe `pps_sync[0]`, the first metastability-catching flip-flop.

If `IRIG_COMP_OUT` is temporarily exposed for comparison, sample it only as another coarse diagnostic and compare the SMA, `IRIG_TRIG_OUT`, and `IRIG_COMP_OUT` transitions with an oscilloscope. The ILA clock period is too coarse to characterize the comparator's analog timing distribution.

Use these initial ILA settings:

| Setting | Initial value |
|---|---:|
| ILA type | Native probes |
| Clock | `clk_adc0`, `76.8 MHz` |
| Probe width | `5` or `6` bits total |
| Capture depth | `1024` samples |
| Trigger position | `512` |
| Capture condition | Always |
| Trigger condition | Rising edge of `pps_sync[1]` |

A `1024`-sample capture spans approximately:

```text
1024 / 76.8 MHz = 13.33 us
```

That is sufficient to inspect synchronization latency and AXI4-Stream handshaking around the PPS transition. Increase the capture depth to `2048` samples for a `26.67 us` window if needed.

A correct waveform should resemble:

```text
IRIG_TRIG_OUT      ___/----------------
pps_sync[1]        _____/--------------
m_axis_tdata[0]    ______/-------------
m_axis_tvalid      --------------------
m_axis_tready      --------------------
aresetn            --------------------
```

The synchronized PPS transition should occur a few `clk_adc0` cycles after the `IRIG_TRIG_OUT` edge observed by the FPGA. That statement covers the digital adapter only; it does not include the PPS input-conditioning delay from the SMA connector. While the HLS kernel is actively capturing, `m_axis_tvalid` and `m_axis_tready` should remain high.

For a reproducible hardware platform, add an `ILA` or `System ILA` IP block in the Vivado block design, select native probes, and wire the signals explicitly. A temporary alternative is to mark nets with `MARK_DEBUG`, open the synthesized design, and run **Set Up Debug**. Use a second linked-design ILA only if the static-adapter ILA shows correct behavior but the HLS capture still fails.

Bring up the trigger path in this order:

1. Configure the RF reference clocks.
2. Program the PPS-enabled bitstream.
3. Open Vivado Hardware Manager.
4. Arm the ILA for a rising edge on `pps_sync[1]`.
5. Send a `1 Hz` PPS test signal.
6. Confirm synchronization and AXI4-Stream handshaking.
7. Increase the trigger rate to `60 Hz`.
8. Run the host capture and correlate completion with the ILA waveform.

AMD documents the ILA clock requirements and waveform viewer in:

- [UG908: Viewing ILA Probe Data in the Waveform Viewer](https://docs.amd.com/r/2023.1-English/ug908-vivado-programming-debugging/Viewing-ILA-Probe-Data-in-the-Waveform-Viewer)

## 14. Concrete RTL and Vivado Integration Recipe
This section is an implementation-ready version of the PPS adapter and ILA steps above. Use it when adding the Schmitt-triggered `IRIG_TRIG_OUT` path to the static Vivado platform. The RTL does not instantiate or program the onboard `SN74AUP1G17DCKR`; that device already conditions the external PPS signal before it reaches FPGA pin `AH13`.

### 14.1 Add the RTL Adapter
Create `pps_trigger_axis.v` and add it to the Vivado project's design sources:

```verilog
module pps_trigger_axis (
    (* X_INTERFACE_INFO = "xilinx.com:signal:clock:1.0 aclk CLK" *)
    (* X_INTERFACE_PARAMETER = "XIL_INTERFACENAME aclk, ASSOCIATED_BUSIF m_axis, ASSOCIATED_RESET aresetn" *)
    input  wire        aclk,

    (* X_INTERFACE_INFO = "xilinx.com:signal:reset:1.0 aresetn RST" *)
    (* X_INTERFACE_PARAMETER = "XIL_INTERFACENAME aresetn, POLARITY ACTIVE_LOW" *)
    input  wire        aresetn,

    input  wire        pps_in,

    (* X_INTERFACE_INFO = "xilinx.com:interface:axis:1.0 m_axis TDATA" *)
    output wire [31:0] m_axis_tdata,
    (* X_INTERFACE_INFO = "xilinx.com:interface:axis:1.0 m_axis TVALID" *)
    output wire        m_axis_tvalid,
    (* X_INTERFACE_INFO = "xilinx.com:interface:axis:1.0 m_axis TREADY" *)
    input  wire        m_axis_tready,

    output wire        dbg_pps_sync_level,
    output wire        dbg_axis_level,
    output wire        dbg_axis_valid
);

(* ASYNC_REG = "TRUE" *) reg [1:0] pps_sync;
reg [31:0] axis_data;
reg axis_started;

always @(posedge aclk) begin
    if (!aresetn) begin
        pps_sync <= 2'b00;
        axis_data <= 32'b0;
        axis_started <= 1'b0;
    end else begin
        pps_sync <= {pps_sync[0], pps_in};
        axis_started <= 1'b1;
        if (m_axis_tready)
            axis_data <= {31'b0, pps_sync[1]};
    end
end

assign m_axis_tdata = axis_data;
assign m_axis_tvalid = axis_started;

assign dbg_pps_sync_level = pps_sync[1];
assign dbg_axis_level = axis_data[0];
assign dbg_axis_valid = axis_started;

endmodule
```

The external trigger input is asynchronous. The `pps_sync` shift register performs the two-flip-flop synchronization before the trigger level is passed to the HLS kernel. The HLS kernel detects the rising edge and freezes one chronological four-channel ADC frame.

### 14.2 Add the Pin Constraint
Create `pps_trigger.xdc` and add it to the Vivado project's constraints:

```tcl
set_property PACKAGE_PIN AH13 [get_ports IRIG_TRIG_OUT]
set_property IOSTANDARD LVCMOS18 [get_ports IRIG_TRIG_OUT]
```

Do not constrain `IRIG_TRIG_OUT` as a clock. It is an asynchronous trigger input that is synchronized by `pps_trigger_axis`.

### 14.3 Wire the Static Block Design
Open `system.bd` and perform these steps:

1. Add an external input port named `IRIG_TRIG_OUT`.
2. Right-click the block-design canvas and select **Add Module**. Add `pps_trigger_axis` as `pps_trigger_axis_0`.
3. Connect:

   ```text
   IRIG_TRIG_OUT
     -> pps_trigger_axis_0/pps_in

   usp_rf_data_converter_0/clk_adc0
     -> pps_trigger_axis_0/aclk

   proc_sys_reset_clk_adc0/peripheral_aresetn
     -> pps_trigger_axis_0/aresetn
   ```

4. Confirm that Vivado groups `m_axis_tdata`, `m_axis_tvalid`, and `m_axis_tready` into the `pps_trigger_axis_0/m_axis` AXI4-Stream interface.
5. In the Vivado Tcl Console, export the interface to Vitis:

   ```tcl
   set_property PFM.AXIS_PORT {
     m_axis {
       type "M_AXIS"
       sptag "PPS_TRIG_AXIS"
       is_range "false"
     }
   } [get_bd_cells /pps_trigger_axis_0]
   ```

6. Run:

   ```tcl
   validate_bd_design
   save_bd_design
   ```

### 14.4 Add an ILA for Bring-Up
Add one `ILA` IP block to `system.bd` and name it `ila_pps`. This ILA is optional for the production image but recommended for the first PPS-enabled bitstream.

Configure the ILA:

| Setting | Value |
|---|---:|
| Monitor type | Native probes |
| Number of probes | `5` |
| Probe widths | `1, 1, 1, 1, 1` |
| Capture depth | `1024` |
| Input pipe stages | `0` |

Connect:

```text
usp_rf_data_converter_0/clk_adc0
  -> ila_pps/clk

pps_trigger_axis_0/dbg_pps_sync_level
  -> ila_pps/probe0

pps_trigger_axis_0/dbg_axis_level
  -> ila_pps/probe1

pps_trigger_axis_0/dbg_axis_valid
  -> ila_pps/probe2

pps_trigger_axis_0/m_axis_tready
  -> ila_pps/probe3

pps_trigger_axis_0/aresetn
  -> ila_pps/probe4
```

The five probes mean:

| Probe | Signal | Expected behavior |
|---|---|---|
| `probe0` | Synchronized PPS level | Rises after the external trigger passes through the two-flip-flop synchronizer. |
| `probe1` | AXI4-Stream trigger level | Follows `probe0` after the registered stream update. |
| `probe2` | AXI4-Stream `TVALID` | Remains high after reset is released. |
| `probe3` | AXI4-Stream `TREADY` | Remains high while the linked HLS kernel consumes the trigger stream. |
| `probe4` | Adapter reset | Remains high during acquisition. |

Run `validate_bd_design` and `save_bd_design` again after wiring the ILA.

### 14.5 Build and Verify the Static Platform
Generate the bitstream and export a new hardware `.xsa` with the bitstream included. Regenerate the Vitis platform from that `.xsa`, then confirm that `PPS_TRIG_AXIS` is present and `clk_adc0` remains fixed clock ID `3` at `76.8 MHz`, as described in Section 6.

For the first ILA-only test, it is sufficient to generate and program the PPS-enabled static Vivado bitstream. At that stage, use `probe0` to verify synchronization of the physical PPS input. The Vitis HLS changes and linked design are required before expecting final AXI4-Stream `TREADY` behavior or testing end-to-end triggered ADC capture.

### 14.6 Test the PPS Input with the ILA
1. Configure the RF reference clocks so that `clk_adc0` is running.
2. Program the PPS-enabled bitstream and open Vivado Hardware Manager.
3. Set the ILA trigger condition to a rising edge on `probe0`.
4. Apply the conservative `1 Hz` pulse waveform from Section 2 to the board's `1PPS` SMA connector.
5. Arm the ILA and capture one trigger.
6. In the static-platform ILA test, confirm:

   ```text
   probe0: synchronized PPS level rises
   probe2: TVALID remains high
   probe4: aresetn remains high
   ```

7. After building the linked Vitis design with the HLS consumer, repeat the capture and confirm:

   ```text
   probe1: AXI4-Stream trigger level follows probe0
   probe3: TREADY remains high while the linked kernel is running
   ```

8. Increase the input rate to `60 Hz` only after the `1 Hz` waveform is correct.
9. Use an oscilloscope, not the ILA, to characterize SMA-to-`IRIG_TRIG_OUT` analog timing accuracy.

### 14.7 Complete the Four-Channel Trigger Migration
After the static PPS path has passed the ILA test:

1. Add `ext_trigger_in` to the HLS kernel as described in Section 7.
2. Remove the ADC_C threshold argument and update the host arguments as described in Section 8.
3. Add the `PPS_TRIG_AXIS:dummy_kernel_1.ext_trigger_in` connection as described in Section 9.
4. Rebuild HLS and confirm that the five-stream acquisition loop still achieves `II=1`.
5. Rebuild and deploy the complete SD-card image.
6. Connect ADC_D, ADC_C, ADC_B, and ADC_A as readout channels and apply the external trigger only to the `1PPS` SMA connector.
7. Capture and plot all four ADC columns.
